## 4. Slow provider and timeout — approximately 4 minutes

**ACTION**  
Select “Slow provider.” Keep timeout at 2,000 ms and two retries. Click **Send request** and wait for the final result.

**WHAT TO SAY**  
“The mock provider holds its response for 4,000 milliseconds. The resilience layer starts a timer for each provider fetch using `AbortController`. At 2,000 milliseconds, it aborts that fetch and records a timeout. Because timeouts are classified as retryable in this experiment, the policy can make another attempt, still subject to the same per-attempt budget and retry cap. At default settings there can be three timed-out attempts, with retry waits between them.”

“A timeout is a latency and resource budget, not proof that the provider computation failed. It says this caller will stop waiting after the configured amount of time. In this implementation the abort signal is attached to the resilience layer’s outbound fetch. The mock route does not propagate the client disconnect into cancellation of its timer or provider work. The simulated delay can therefore finish after the caller has stopped waiting. I should not describe this as guaranteed downstream cancellation.”

“Waiting too long can hold request and application resources, consume concurrency, and push the caller beyond its own service-level objective. Setting the timeout too low has the opposite problem: normal variation can be labeled as failure, and retries can add load even though the provider might soon have responded. The value needs to be chosen from the application’s latency budget and observed provider behavior.”

**WHERE / HOW**  
In `server/resilience.js`, point to `providerAttempt`: the `AbortController`, timeout `setTimeout`, `fetch(..., { signal })`, and `finally` cleanup. Point out the `TIMEOUT` error classification and retry path in `runResilientRequest`. In `server/mockProvider.js`, show the 4,000 ms wait.

**WHAT TO LOOK FOR**  
Read each “timeout budget 2000 ms,” timeout event, retry wait, and final attempt limit from the trace. The metric’s duration includes all timed-out attempts plus waits. Runtime timings may differ slightly due to scheduling.

**WHY IT MATTERS**  
The timeout limits caller-side waiting on an individual downstream attempt. It does not necessarily cap the entire logical operation at the same value: bounded retries and backoff can make total duration much longer. A production design may also need an overall deadline; this demo intentionally focuses on per-attempt timeout plus bounded retries.

**VERIFICATION**  
Confirm the trace distinguishes the configured timeout budget from provider modeled latency, and that attempts do not exceed one plus maximum retries. Mention that a client timeout can overlap provider work that is not cancellable.

## 5. Transient failure and bounded retry — approximately 4 minutes

**ACTION**  
Select “Transient HTTP 503,” leave maximum retries at two, and send one request.

**WHAT TO SAY**  
“The mock is deterministic within a logical request. `mockProvider` returns 503 on physical attempts one and two, then 200 on attempt three. The client sees an unavailable response, classifies it as retryable for this experiment, waits according to policy, and tries again. The third attempt succeeds.”

“Maximum retries means retries after the initial call. Two retries therefore allow at most three physical attempts. It does not mean two total attempts. This policy is bounded: if the dependency stays unavailable, it stops instead of retrying forever. Boundedness caps extra load and gives the caller a finite retry count, although total wall-clock time still depends on timeout and backoff.”

“Retrying can help if a failure is temporary and the operation is safe to repeat. It cannot make a persistent outage disappear. Even a successful retry increases latency compared with a single attempt. A successful final outcome should be interpreted alongside its attempt count and duration.”

**WHERE / HOW**  
Show the `attempt <= 2` branch in `mockProvider.js`; show the loop limit `attempt <= config.maxRetries + 1` and the `RETRYABLE_STATUSES` set in `resilience.js`.

**WHAT TO LOOK FOR**  
Read the three provider statuses, classification events, waits, final HTTP 200, retry count two and total duration. The wait values are runtime values because full jitter is on.

**WHY IT MATTERS**  
A final success alone hides transient instability. Trace-level physical attempt evidence tells us how the logical request was completed and what extra traffic it generated.

**VERIFICATION**  
Confirm sequence 503 → 503 → 200 and exactly three attempts with the default retry limit. Change maximum retries to one only if you want to demonstrate early termination; restore two for the later concurrent run.

## 6. Retry classification — approximately 3 minutes

**ACTION**  
Select “HTTP 400” and send one request. Then run HTTP 500 and HTTP 429 to compare the configured policy.

**WHAT TO SAY**  
“HTTP 400 represents an invalid request that is deterministic until the input changes. In `isRetryableStatus`, 400 is absent from the retryable set. The trace should say NOT RETRYABLE and stop after one physical call. Retrying the same malformed request consumes capacity without changing the cause.”

“This experiment treats 500, 502, 503, 504 and 429 as potentially retryable statuses. That is a policy choice for this lab, not a universal rule. Whether a server error is transient depends on provider behavior and operation semantics. A 429 is a rate-limit signal, so the server’s timing guidance matters. Here `Retry-After: 1` is parsed and the applied wait is at least one second; jitter does not shorten that minimum.”

“Retries also need safe operation semantics. A read-only generation request may be repeatable from the caller’s perspective, but some APIs can trigger billing, tool actions, or other side effects. Retrying a non-idempotent operation can duplicate effects unless the system has appropriate protections such as an idempotency key or deduplication strategy.”

**WHAT TO LOOK FOR**  
For 400: HTTP 400, NOT RETRYABLE, stopped, one attempt. For 500: repeated 500 responses up to the configured attempt limit. For 429: Retry-After guidance followed by the effective wait. Read the actual trace, not assumed values.

**VERIFICATION**  
Confirm classification is in code, not inferred from status color. Identify the `Retry-After` header response in `server.js` and its parsing in `retryAfterMs` in `resilience.js`.

## 7. Immediate retry problem — approximately 2 minutes

**WHAT TO SAY**  
“Consider one thousand simultaneous logical requests and a policy allowing two retries. If every request reaches all three attempts, the simplified upper bound is three thousand physical provider attempts. That is not an assertion that every run always creates exactly three thousand calls; successes, non-retryable errors, cancellation, and timing change the actual number.”

“If each client retries immediately after an outage response, it can add traffic at the point the dependency is already struggling. That amplification can prolong recovery and make a brief problem worse. The application lets us inspect the cost through attempt counts; it does not expose a separate immediate-retry switch. I’m comparing immediate retry conceptually with the measured configured backoff.”

**WHY IT MATTERS**  
A retry is another downstream request. It should be accounted for as additional load and latency, not as a free reliability improvement.

**VERIFICATION**  
Relate the number of logical requests to maximum physical attempts using the selected retry cap. Label 3,000 as a maximum in this simplified example.

## 8. Exponential backoff — approximately 4 minutes

**ACTION**  
Return to Transient HTTP 503. Use base delay 500 ms, exponential backoff on, and temporarily turn jitter off so the scheduled caps are easy to compare. Send a request; then re-enable jitter for the remaining run.

**WHAT TO SAY**  
“`calculateBackoff` in `server/resilience.js` uses `baseDelayMs * 2 ** retryIndex` when exponential backoff is enabled. Retry index is zero-based. The first retry after attempt one uses index zero, so 500 times two to the zero is 500 milliseconds. The next retry uses index one, so it is 1,000 milliseconds. With a third retry it would be 2,000 milliseconds. Our default cap of two retries only uses the first two waits.”

“When jitter is off, the requested delay equals this cap. The trace reports the calculated backoff and the wait before the next attempt. With full jitter on, the code selects an integer uniformly from zero through the cap, inclusive. The trace shows both the cap and the selected delay. So the actual waits are variable, and the selected value is never greater than the cap.”

“Backoff gives a dependency time to recover and spaces repeated attempts. It also adds directly to end-to-end latency. Here a logical request’s total time includes provider attempt durations, timeout periods where applicable, and retry waits. Production retry limits and delays must fit the caller’s overall latency objective. A per-attempt timeout alone does not guarantee an overall deadline.”

**WHERE / HOW**  
Read `calculateBackoff`, especially `retryIndex = attempt - 1`, `2 ** retryIndex`, and `Math.floor(Math.random() * (rawDelayMs + 1))`. Then point to the trace event construction in `runResilientRequest`.

**WHAT TO LOOK FOR**  
With jitter off: first wait 500 ms and second wait 1,000 ms. With jitter on: first selected wait is between 0 and 500 ms; second between 0 and 1,000 ms. In 503 sequence these precede attempts two and three respectively.

**VERIFICATION**  
Check trace values rather than relying only on formula narration. The first retry index is zero, not one. Return jitter to ON after the explanatory comparison.

## 9. Jitter — approximately 3 minutes

**WHAT TO SAY**  
“Exponential backoff without jitter still produces the same schedule for clients that fail together: 500 milliseconds, then 1,000 milliseconds. If a large population receives an outage at once, many clients can wake and retry at those same boundaries. That synchronization can create a retry storm or thundering herd.”

“This implementation uses full jitter. For each retry it first calculates an exponential cap, then independently samples a whole number of milliseconds from zero through that cap. That spreads retry times across the interval rather than placing all callers at its upper endpoint. The trade-off is less predictable per-request timing. The cap remains explainable and bounded, but individual values vary.”

“Jitter is not a rate limiter and does not enforce a global request budget. It reduces synchronized arrival patterns; it does not guarantee the total retry traffic is safe. Bounded attempts and appropriate concurrency controls remain design considerations outside this demo’s scope.”

**WHERE / HOW**  
Show the `jitter` boolean in the controls and the full-jitter sampling formula in `calculateBackoff`.

**VERIFICATION**  
Use the next five-client run to read observed values. They should vary in the range allowed by each exponential cap; random samples can occasionally be equal, so interpret the observed distribution rather than promising five unique values.

## 11. Trade-offs — approximately 2 minutes

**WHAT TO SAY**  
“A shorter timeout frees the caller sooner but risks false timeouts under normal latency variation. A longer timeout reduces that risk but can consume resources and violate the caller’s latency objective. More retries may raise the chance that a transient error recovers, while also increasing worst-case work and retry amplification.”

“Larger backoff caps give a struggling provider more recovery time but add user-visible latency. Jitter reduces synchronized timing while making exact completion time less predictable. There is no universal best set of values. The appropriate policy depends on provider latency distributions, operation semantics, caller deadlines, and the cost of extra attempts.”

“Retryable is a classification decision, not a promise of eventual success. A system should stop within a bounded policy and surface failure clearly when it cannot complete.”

**VERIFICATION**  
Tie each trade-off to a visible control or result: timeout slider, retries, base backoff, jitter toggle, request duration, and attempt count.

## 12. Final conclusion — approximately 2 minutes

**WHAT TO SAY**  
“This implementation demonstrates how a client can protect an LLM integration from slow and temporarily failing downstream calls. A timeout limits how long the caller waits on each attempt. Failure classification prevents deterministic client errors such as HTTP 400 from triggering pointless repeats. Bounded retries allow limited recovery opportunities without retrying forever. Exponential backoff increases the time between retries, while full jitter spreads retry timing among clients that would otherwise follow identical schedules.”

“The experiments also show the costs. Retries add physical provider calls and latency; a timeout does not prove downstream work stopped; rate-limit guidance must be respected; and retry safety depends on whether an operation can be repeated without duplicate side effects. These mechanisms can improve resilience against transient failures, but they do not guarantee availability. Timeout and retry settings should be selected against the application’s latency budget, observed provider behavior, and operation semantics, then validated with real operational evidence.”

Summarize the observed HTTP statuses, attempt counts, delays, and durations from the live run. Mention any browser console issue or skipped experiment explicitly. The application code was already prepared; this session analyzed and validated its behavior.
